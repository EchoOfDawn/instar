## What Changed

- `src/feedback-factory/execute/executorPorts.ts`: `fetchBase` also refreshes a local branch `feedback-execute/base` and reads the base from it. An attempt clone copies only objects reachable from the checkout's branches, so a base that only `origin/main` reached failed every attempt with "unable to read tree".
- `src/feedback-factory/execute/FeedbackExecutorService.ts`: the claim loop stops after the first failed preparation; the scrubbed failure message is kept in executor state and shown as `status.lastPrepareFailure`, and the audit row carries a `step` label (the id-only audit had blanked the message to `[text:300]`).

- `src/feedback-factory/execute/buildFeedbackExecutor.ts` + `src/server/AgentServer.ts`: the update-pending admission brake holds only when an update restart is actually coming (`autoApply` on and an update pending). With auto-apply paused, a detected newer version refused every tick, though no restart would come.

Why: live 2026-10-23 18:33 PDT, one tick failed 8 work items in two minutes for the same machine-level reason; from 22:30 PDT every tick was refused as update-pending while auto-apply was paused.

- **The passkey health digest no longer posts when nothing needs a person.** The digest lists passkey cells that need a human, pending revokes, Chrome gate failures and a suspension. It also appended a line naming peers the pool could not read. When that peer line was the only content, the digest still counted as non-empty, so every change in peer reachability (a laptop going to sleep, a partitioned PC) re-posted a "Passkey health: 0 cell(s) need attention" item into the Attention topic. On the dev agent that was 147 of 341 Attention posts in three days. A digest whose only content is the peer line is now empty: nothing posts, and an already-open item resolves silently. When something real is listed, the peer line still appears beside it, as before.

## What to Tell Your User

Feedback fixes can start again: a setup step was failing for every item. If setup ever fails again, the pipeline stops after one item instead of working through the whole queue, and the reason shows on its status page.

The Attention topic stops getting "Passkey health: 0 need attention" messages. You'll only hear about passkeys when one actually needs you. Whether your other machines are reachable is still shown on the Machines dashboard tab.

## Summary of New Capabilities

- `GET /feedback-factory/execute/status` → `lastPrepareFailure` `{ at, attemptId, reason, step, detail }`.
- Audit `execute:prepare-failed` carries `step`.

None. This removes a noisy notification; no new capability.

## Evidence

`execute-attempt-git.test.ts` (base reachable only from origin/main still checks out; fails without the fix), `execute-reroute-capacity.test.ts` (one failed preparation per tick, readable reason), `execute-wiring.test.ts` (update-pending only with autoApply on). Executor unit 145/145, integration 9/9, e2e 2/2, lint clean.

The "update pending" pause on the feedback executor now lapses after 6 hours, so an update that keeps failing to install can no longer stop the executor forever.

- Dev agent (Mac Studio, Attention topic, 2026-10-20 to 2026-10-23): 147 of 341 Attention-topic posts carried `Source: passkey-health`, and the visible ones read "0 cell(s) need attention" with only the "Peers unobserved by the pool read path: Laptop (peer-offline), Mama PC (partitioned)" line.
- Cause: `buildPasskeyHealthDigest` set `body` non-empty whenever any line existed, including the unobserved-peer line, so `PasskeyDigestLedger.decide` returned `silent` (an upsert, which posts a message in the single Attention hub) on every peer change.
- New unit test in `tests/unit/passkey-cell-health.test.ts`: a peers-only digest is empty, decides `none` with no open item, and `resolve` when an item was open. File passes (11 tests).
