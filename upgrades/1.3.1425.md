## What Changed

When an outbound reply cannot be sent, the agent keeps it and raises an attention
item saying it "is held durably and retried on the recovery schedule". Two
different kinds of hold shared that sentence, and for one of them it was false.

A **forwarded** hold — the reply is handed to the machine holding the serving
lease, and the handover fails — genuinely is retried, and often succeeds.

A **direct-path** hold is taken when this machine sealed the record before
discovering it does not hold the lease. A sealed record is bound to the machine
that produced it, so it **cannot be forwarded at all**. Nothing retries it. It can
only be sent if the lease returns to that machine, and otherwise it expires.

The direct-path notice now says exactly that. Delivery behaviour is unchanged.

- The idle check's list of "resident helper" processes now recognises any MCP server by the `mcp` token in its command line (`workspace-mcp`, `@plaud-ai/mcp@latest`), instead of only the handful it named by hand. A conversation whose only children are its MCP servers is idle again, so the idle timer starts and idle conversations are closed on schedule.

- `src/core/paneText.ts`: `meaningfulNonBlankTail(text, n)` (last n non-blank rows).
- `src/core/SessionManager.ts`: the resolver pre-gate and its evaluate capture read non-blank rows (`captureMeaningfulNonBlankTailMaybeAsync`, 80-row physical window); the pre-gate regex is the exported `RESOLVER_PREGATE_RE`.
- `src/monitoring/PermissionPromptAutoResolver.ts`: Layer 3 (`detectPersistingMenu`) ignores trailing transient lines (`stripTransientTrailer`: retry-wait line, permission-mode status bar) and uses a 12-line bottom window; it audits `menu-observed` on first sight and `menu-unanswered-terminal` on the raise. Layer 2 is unchanged.

**The pre-push gate refused every push once its review check aged out, even when every
pending change had already been reviewed.** The check asked whether any side-effects
review had been written in the last 24 hours. Release notes accumulate across many
already-reviewed changes until a release folds them away, so a fully-reviewed batch
started failing purely because time passed. It now asks whether a review is at least as
recent as the newest pending change — which never rots on its own.

Telegram updated Telegram Web K (build 2.2 (679)) on 2026-10-16. The typed Telegram browser route held correctly but silently: peer resolution refused the unknown build on a path that never recorded the failed build or raised the attention item the origin spec requires, and there was no runnable way to enroll a newly reviewed build.

- Browser reads (snapshot, peer resolution) now use the same bounded recovery as sends: one fresh-process recheck, then the failed build is recorded (`GET /telegram/origins/status` → browser recovery `failedBuilds`) and exactly one attention item is raised per failed build.
- Build 679 was reviewed against its public source maps (every driver contract unchanged; evidence in `docs/specs/reports/telegram-message-origin-evidence/web-k-2.2-679-review.md`) and added to a reviewed-build list.
- New local command `instar telegram-origin enroll-browser <profile>`: runs a read-only canary on the managed profile and enrolls the observed build only if it is on the reviewed list, keeping one prior reviewed build. Deliberately not an HTTP route. The running server picks the new enrollment up at its next browser start, without a restart.
- CLAUDE.md template and `migrateClaudeMd`: Web K update paragraph; attention wording corrected to "per failed build".

- **The local verifier's version fingerprint no longer depends on a neighbouring folder.** `computeVerifierVersion()` (`src/localVerify/verifierVersion.ts`) hashed `typescript:<version>`, read by Node's module lookup from the installed package. That lookup walks up through parent folders, and from `.instar/shadow-install/node_modules/instar` it reaches the agent home's own `node_modules`, which an unrelated `npm ci` empties and refills. The fingerprint therefore flipped between two values across server restarts (`vh2:25b6e0cc…` with typescript 5.9.3 found, `vh2:da61a7a1…` with it absent), and every flip voided every pending local-verify record (`verifier-mismatch`), so PRs re-tested after each restart. The input is removed: nothing outside the package is read any more. The skip ratchet already loads its parser from the PR's own worktree (PR #2326), so the TypeScript version was never a property of the verifier. The salt and prefix move to `local-verify-verifier-v3` / `vh3:`, so records written under `vh2` re-verify exactly once and can never collide with a `vh3` value.

Every PATCH and PUT route on the local server now refuses a request carrying a field it does not apply, with 400, the unsupported field names and the supported list, and changes nothing. Before, about twenty routes applied the fields they knew, ignored the rest and answered 200. `PATCH /attention/:id` now stores `resolution` (alias `reason`) instead of dropping it. `PATCH /api/files/config` now applies `{"enabled": false}`, which the dashboard feature switch sends: the file viewer turns off at once and stays off after a restart. Before, it answered `updated: true` and stayed on.

## What to Tell Your User

If your agent ever tells you a reply is stuck, the notice now distinguishes
between one it is retrying and one it cannot send at all. Previously both said a
retry was coming, which made the second kind look like something to wait out — and
waiting is exactly what does not help, since those expire undelivered unless the
right to speak returns to that machine.

- If I run a Google Workspace, Plaud or similar helper in every conversation, my idle conversations are now cleaned up on the normal schedule instead of staying open forever and eventually blocking new ones. A cleaned-up conversation resumes the moment you message it.

If one of my sessions gets stuck on a menu I will not answer for you (a model-switch question, a confirmation for a risky command), you now get one attention notice after it has sat there for about a minute, even when the menu is not at the very bottom of the screen. Nothing is answered for you: I still only ever auto-approve the one harmless prompt I was built for.

When Telegram updates its web app, my Telegram browser sending pauses until I've checked the new version is safe. Before, that pause happened quietly. Now you get one heads-up in the attention topic, and I can re-approve a checked version myself without restarting anything. Nothing is ever sent while it is paused.

Nothing to do. On a maintainer agent, pull requests waiting on the local test run no longer lose their green result every time the server restarts; after this update each pending result is re-checked once, and from then on only a real change to the verifier, its policy or Node starts the checks over.

If you switch the dashboard file viewer off, it is now really off straight away. Before, the switch said it worked and the viewer stayed on.

## Summary of New Capabilities

None — this corrects the wording of an existing notice. No delivery behaviour
changes; the same replies are held, retried or expired as before.

- None new: an existing cleanup now works on agents that run MCP helpers whose names do not say "server".

- A parked menu under blank padding or a status line is noticed and announced once.
- `logs/permission-prompt-resolver.jsonl` records every menu the resolver saw and declined to answer, so a silent stall is no longer indistinguishable from a quiet session.

- A Telegram web update that pauses browser sending now raises one attention item instead of failing silently.
- `instar telegram-origin enroll-browser <profile>` re-enrolls a reviewed Telegram Web build after a read-only check.

None. A fix to an existing fingerprint; no new routes, config or state.

- Attention items keep the resolution text given when they are closed.
- Turning the dashboard file viewer off works.

## Why It Matters

The only way to satisfy the old rule was to write a redundant review for work that
already had one, or re-touch an existing file to reset a clock. The gate's own source
records three prior occasions where someone wrote a placeholder to get past it. A check
whose sole remedy is to produce a junk document trains the wrong habit while pretending
to enforce a standard.

Unreviewed work is still refused: a new note outruns every existing review and the gate
still stops the push.

## Action Required

None. Behaviour is automatic and local to each machine's pre-push hook.
