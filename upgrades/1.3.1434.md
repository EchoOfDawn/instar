## What Changed

- New constitutional standard *Avoid TCC-Protected Directories — No Agent State Under ~/Documents on macOS* (`docs/STANDARDS-REGISTRY.md`): no agent home, project directory, worktree, state directory, vault, database or log may live under `~/Documents`, `~/Desktop`, `~/Downloads` or iCloud Drive on macOS. Operator mandate 2026-10-14 after a TCC grant withdrawal killed two agents in the same second.
- `instar init` (fresh, existing-directory, standalone) now REFUSES a protected target on macOS before writing anything, with the reason, the safe alternatives and the runbook. No override. Linux is unaffected (the check is platform-gated and never fires there).
- At server boot a new always-on guard (`src/core/TccProtectedPathGuard.ts`, manifest row `monitoring.tccProtectedPathGuard`, load-bearing) classifies the project + state directories, prints one loud `TCC-PROTECTED PATH` line when they are inside a protected folder, raises ONE deduped HIGH attention item naming the path and the runbook (JSONL fallback at `<stateDir>/audit/tcc-protected-path.jsonl` without Telegram), and reports on `GET /guards`. It never moves or deletes anything.
- `instar doctor` gains a `Project location` check (fail + runbook pointer when protected).
- Migration parity: `PostUpdateMigrator.migrateTccProtectedPath` re-surfaces the condition in the migration summary on every update until the agent is moved; the CLAUDE.md awareness section (`TCC-protected path guard`) reaches new and existing agents.
- Runbook `docs/runbooks/move-agent-out-of-documents.md`: the operator-proven move (rename on the same disk, symlink at the old path, launchd plist update, reload, verify).

- `src/feedback-factory/execute/executePolicy.ts`: `systemTempDenies(workspace, attemptTmpDir?)` now drops a shared system temp directory from the deny list when it is an ancestor of the workspace **or** of the attempt's own temp directory, comparing by the deepest EXISTING ancestor's real path with the remainder re-appended (`/tmp` is a symlink to `/private/tmp` on macOS and `/private/tmp` resolves to `/tmp` on some Linux hosts, and an attempt temp that does not exist yet cannot be resolved at all — so a plain `realpathSync` leaves one side lexical and the exemption silently does nothing). Both callsites in `buildSandboxRuntimeSettings` (`denyRead` and `denyWrite`) pass `p.tmpDir`.

Why: `shortAttemptTmpDir` deliberately places each attempt's temp directory under the real `/tmp` because unix socket paths must stay short, and the sandbox runtime documents that for WRITES `denyWrite` takes precedence over `allowWrite` (the reverse of reads, where `allowRead` wins). So `denyWrite: ['/tmp','/private/tmp',…]` overrode `allowWrite: [...,'/private/tmp/fb-<id>']` and the attempt could not create a directory inside its own temp: `EPERM: operation not permitted, mkdir '/private/tmp/fb-8ac70c2cde/HH0KfR7JCSG9zBDVFZQSa'`, thrown by vitest's config resolution. That is the `base-unit-smoke` probe failure that latched the feedback executor for three days (2026-10-22 → 2026-10-25, five consecutive 24h latches). `base-lint-gate` passed the whole time because `npm run lint` never creates a directory under `TMPDIR`; vitest does. The rule already exempted an ancestor of the workspace — a case that never fires in production — and not the attempt temp, which always does. A pre-existing test (`execute-short-attempt-tmpdir.test.ts`) asserted the broken pairing as the intended policy, which is why it shipped; it now asserts the real invariant instead, with the history recorded beside it.

Found by reading the probe's own captured stderr, which exists because of `b84149fce` hours earlier; before that the entire record was `exit 1`. Two prior hypotheses were wrong: the npm cache redirect (kept, harmless, matches the adjacent precedent) and the host test-runner semaphore — the captured output shows that EPERM explicitly followed by `— admitting the run (fail-open)`.

## What to Tell Your User

On a Mac, the Documents, Desktop, Downloads and iCloud Drive folders are guarded by the system's privacy controls, and the system can revoke access to them for every running agent at once — that is what took two agents down on 14 October. From now on I will not set up a new agent inside those folders, and I will tell you clearly (at startup, in the doctor health check, and on each update) if an existing agent still lives there, with a short runbook for moving it. I never move anything myself. Agents on Linux are not affected.

The safety rehearsal that runs before the pipeline writes a fix was refusing the pipeline's own scratch folder, so the test step inside it died instantly. That is fixed, and the stop it caused can now be cleared without waiting out a day.

- Side-effects review with an independent second pass: `upgrades/side-effects/avoid-tcc-protected-directories.md`.

`execute-units.test.ts`: a system temp that is an ancestor of the attempt temp is dropped from the deny list (by real path, both the resolved and unresolved spellings); the other shared temps are still denied; with no attempt temp under it the system temp stays denied; and at the settings level no `denyWrite` entry is an ancestor of `p.tmpDir` while `allowWrite` still contains neither `/tmp` nor its real path. Mutation-verified three ways: reverting the exemption fails, over-exempting fails, and a leaf-only `realpathSync` instead of the ancestor-resolving comparison fails — that last one is the defect the first cut of this fix actually shipped with, caught by the rewritten pre-existing test. 46 files / 643 tests green in `tests/unit/feedback-factory/`; lint and typecheck clean.

Honest residue, stated in the side-effects artifact: `denyRead` also stops carrying the ancestor. For writes the safety rests on allowlist semantics plus the canary's `bash-write-system-temp` must-fail probe, which proves it every run. For reads there is no equivalent per-run probe, so that arm rests on reasoning.
